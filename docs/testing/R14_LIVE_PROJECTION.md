## Decision and measured scope

Keep `activeBuses/{busId}_{routeId}` authoritative for telemetry, lifecycle and matching. Splitting these owners requires moving traces showing retries/write latency after bounded processing, not an emulator concurrency fixture alone. R14 instead filters irrelevant engine events before queue admission and gives browsers a separate compact route materialization.

The loopback experiment in `backend/src/liveBusProjection.integration.test.ts` uses 20 synthetic fixes, with three concurrent SDK transactions per fix against the same node (telemetry identity plus two metadata changes). Warm results on Windows, Node 26.8.2, RTDB emulator 4.11.2:

| Mode | Callback attempts/fix | Value events/fix | JSON bytes/fix | Relevant lifecycle intakes/fix |
|---|---:|---:|---:|---:|
| Speculative local events | 3 | 3 | 147.6 | 1 |
| Committed-only local events | 5 | 2 | 98.4 | 1 |

Committed-only transactions suppress proposed local state before acknowledgement. This reduces event bytes here, but adds callback retries when same-connection writes overlap. It does **not** demonstrate lower transaction contention. Adopt it for authoritative telemetry/matcher writes so engine and public-view listeners consume acknowledged state; preserve the independent rate-limit reservation behavior. Moving acceptance must measure this retry/latency tradeoff. Existing lifecycle worker transactions already use committed-only callbacks.

The final canonical bounded payload fixture uses 100 buses across 10 routes, raw/matched positions, four trajectory points, a plausibility anchor and worker/context metadata. It includes route/node prefixes and the receipt-vector catalog contract:

| Payload | UTF-8 JSON bytes |
|---|---:|
| Raw fleet, 100 buses | 86,571 |
| Public selected route, 10 buses | 4,318 |
| Route catalog including receipt-vector contract | 811 |

Route plus catalog is 5,129 bytes (94.1% smaller in this fixture). The original pre-prefix/count-only PR #277 fixture totaled 4,789 bytes; the final contract deliberately adds those bytes. These are serialized application values, excluding protocol frames, geometry/configuration, listener initialization overlap and billing overhead. They are not production usage or end-to-end latency measurements. Passengers intentionally tracking a joined ride on another route subscribe to that second route too.

The successor's actual SDK/emulator publisher measurement uses two routes with one bus each. After startup settles, route A receives 20 sequential accepted samples, each followed by one matched-location write and two internal metadata writes. In this exact workload the raw listener receives 80 callbacks / 78,611 decoded JSON bytes; selected route A receives 40 callbacks / 14,734 bytes. The 40 internal changes enter no extra materializations. A subsequent route B update produces zero route A callbacks. Catalog counts remain unchanged, so this interval has zero catalog callbacks/writes; preview receipt changes do update the catalog and must be included in moving measurements.

The same interval dispatches 40 source reads / 17,626 source-value bytes, 80 route-transaction callback attempts, 40 commits and 13,894 committed public bus-value bytes. These counters exclude startup/replay work, protocol overhead and billing. Reconstruction read/byte deltas are zero in this post-startup sample interval. Catalog counters now expose attempts, commits and decoded public-value byte estimates; receipt vectors cost more than the historical count-only catalog. The real publisher, generation takeover, canonical legal IDs, backfill readiness, completion markers and missing-view reconstruction passed nine actual-SDK cases in the loopback emulator. ## Ordering, ownership and recovery

- Durable lifecycle input remains FIFO per bus. Only fields unused by lifecycle are excluded from the admission fingerprint; same-fix session, direction, completion, presence and turnaround changes remain eligible. Errors clear admission fingerprints, and replay bypasses deduplication.
- The elected worker owns public views. Positions use bounded latest-pending scheduling (2 active, 64 pending, 5-second queue age); publications also serialize per route. Dispatch reads current source authority rather than an old queued/replayed session. Rejected/failed publications request bounded reconciliation.
- Public route parent transactions retain private worker generation and revision outside the readable `buses` subtree. Identical successor snapshots still stamp the successor generation without advancing the revision; structural comparison ignores SDK object-key order while retaining unknown-field cleanup. The elected generation is captured before SDK callbacks, which may execute outside the original async context. Catalog revisions are scoped by private per-route generation lineage, so a missing destination can rebuild without being blocked by an old generation's larger revision; same-generation older publications remain rejected. Each first route replay page reads its fixed catalog revision and floors an erased/reset destination above that observed lineage; existing newer revisions survive. This repairs destination loss within the same generation without adding a read per telemetry fix. Registration precedes publication, making crash-created views discoverable during recovery.
- Startup/periodic reconciliation uses source/view pages of 25 and one catalog route at a time; it repairs absent publications and missed removals. Terminal and removed source records do not become active catalog rides. Sessionless previews expire; active rides remain discoverable during signal loss.
- Passenger listeners read `publicRouteBuses/route:{routeId}/buses`, whose opaque children use `node:{sourceKey}`. Only administrators with the trusted boolean claim read the public fleet root. `liveRouteCatalog/values` carries canonical prefixed counts/receipt freshness, never locations. Bare legacy route/node entries are excluded from browser consumption, so coexistence cannot duplicate buses or override canonical counts. Raw authority has no client read access. Existing authenticated HTTP fleet snapshots retain their current fleet-wide behavior with the same explicit public whitelist. Selected-route SDK/UI subscriptions exclude other-route payloads; this does not deny cross-route access through that compatible authenticated HTTP API.
- Frontend route stores share listeners, release idle scopes, and reject callbacks after detach or an auth-verification generation change. Reconnect/retry and joined-ride observation survive route switching.
- A public schema 1 ready marker is generation-fenced and published only after bounded backfill and accepted pending work settle. Missing/incompatible/not-ready markers and either permission-error channel show an actionable error with Retry. Empty fleets require compatible readiness. Selected and explicitly joined routes must both deliver authoritative snapshots before recovery becomes ready; cached or expiry notifications do not certify it. Stale-auth cached data is withheld.
- Natural completion writes one bounded last-completion marker before automatic turnaround. Older/cross-route joined-session recovery uses the member-authorized closed status GET backed by durable sessions, with one visible/online request at a time and 15-second nonterminal checks. `interrupted`/`failed` never create completion or feedback. The marker preserves only the last completion; it is not unbounded ride history.
- Shutdown drains to an eight-second deadline, retains live pending promises only, and rejects publications after stop or leadership revocation, including transaction retries. RTDB cannot atomically read the Firestore lease; destination generation fences retain this documented cross-store limitation.

The materializer adds one source read per dispatched bus publication, a route-parent transaction and occasional catalog updates. Replay adds bounded reads, including one fixed catalog-revision read per route page origin, exposed as reconstructionReads/reconstructionReadBytes. This is an explicit privacy/egress versus backend work tradeoff. Within-route serialization avoids competing public writers on the same elected worker; it does not establish capacity for an arbitrarily large route.

## Protected rollout and moving measurement

1. Deploy the backend worker first while existing browser rules/client remain available. Confirm leadership, canonical prefixed backfill/public-view coverage, repaired empty/missing destinations, and current-generation `clientProjectionStatus/public = {schemaVersion:1,ready:true}` through trusted admin tooling. An empty fleet legitimately has no active bus projection after readiness is established.
2. Apply the matching restrictive RTDB rules, then release the new browser bundle after coverage/readiness are verified. The status endpoint and exact receipt catalog must be available first. Old cached tabs requesting raw authority receive permission denied and need to refresh to the new release. Testing merges do not deploy the worker, rules or browser; no cloud rules were deployed in this task. Do not claim a seamless rolling client migration.
3. For rollback, restore the previous browser/rules release together; retain authoritative source data. The materialized view can remain unused. Do not grant passenger fleet-root access as a fallback.
4. Capture at least 1,000 accepted moving fixes across normal, weak-network and reconnect windows. Compare telemetry `rtdbTransactionAttempts`/write latency, `workQueues.filteredLifecycleEvents`, `workQueues.publicProjection` events/skips/source reads/attempts/commits/public-value bytes, and existing frontend payload/listener traces. Use deltas from the same window and count raw and matched publications separately. `publicBytes` counts committed projected bus JSON values, not total network bytes or catalog transactions.
5. Revisit separate telemetry/lifecycle/match ownership only with those measurements and the correlation/session/route-version contract in `TELEMETRY_STATE_PARTITION_DECISION.md`. Deploying or certifying live production is outside this PR's verification evidence.
