## Summary
PR #103 replaces the system-clock-based telemetry time (`time(nullptr)`/`gettimeofday`) with a 64-bit GNSS epoch anchored to the monotonic millisecond counter (`projectEpochMilliseconds`), keeping telemetry readiness and timestamps correct past the 2038 `time_t` wrap on the ESP32; `time_t` remains only for the platform clock (`settimeofday`), TLS/SNTP, and as a fallback. The fix is minimal, the arithmetic is verified correct (including the 32-bit monotonic wrap), and the new tests exercise the post-2038 conversion and wrap projection. Three minor/nit items follow; nothing blocks merge.

## Findings
- [MINOR] hardware/src/main.cpp (diff hunk at old 358/new 359–381) — GNSS projection has no reference-staleness cap. `epochMilliseconds()` uses `latestGnssReferenceValid` unconditionally, so the projection `ref + (now − ref)` is ambiguous once `now − ref` exceeds 2^32 ms (~49.7 days of continuous uptime with no fresh GNSS sentence; the reference is refreshed only on fresh sentences per GNSS_UTC_MAX_AGE_MS=2000). Past that, timestamps jump ~49.7 days stale and the backend will reject them (`stale_or_invalid_timestamp`). The codebase already has a freshness pattern (`now - latestGnssReferenceAt <= GNSS_UTC_MAX_AGE_MS * 2`, main.cpp:629) that this new primary path doesn't follow. Suggested fix: cap the accepted elapsed (e.g., clear `latestGnssReferenceValid` or fall back when `elapsed(latestGnssReferenceAt)` exceeds a large bound). Low probability for a vehicle-powered fleet (monotonic clock resets each boot), hence MINOR.
- [NIT] hardware/src/main.cpp:632 — `onNtpTimeSynchronized` still inlines the same projection (`latestGnssEpochMs + static_cast<int64_t>(now - latestGnssReferenceAt)`) instead of reusing the new `eki::clock::projectEpochMilliseconds`; duplication risks future drift between the two formulas.
- [NIT] hardware/test/test_telemetry_policy/test_main.cpp — coverage is header-level only: the native env uses `test_build_src = no` (hardware/platformio.ini), so main.cpp's `epochMilliseconds()` fallback decision, `clockIsSynchronized()` readiness, and the log-once range-guard path are not exercised by any automated test. Tests added do exercise the new pure logic (2040 conversion and wrap projection); the integration paths are covered only by the esp32dev build.
- [NIT] main.cpp (new `epochMilliseconds()`) — the `epochMs >= TRUSTED_EPOCH_MIN_MS ? epochMs : systemEpochMilliseconds()` branch is effectively unreachable when the reference is valid (the stored epoch is pre-validated ≥ TRUSTED_EPOCH_MIN_MS and elapsed ≥ 0). Harmless safety net; could be simplified or documented.

## Test assessment
The two added assertions are correct and on-point: `utcToEpochMilliseconds({2040,1,1})` returns `2208988800000` ms (> `2147483647000`), proving the 64-bit path, and the wrap projection (`UINT32_MAX - 500` → `499`, expected `+1000`) exactly exercises the wrap-safe subtraction with the right expectation (verified by hand). Existing `shouldApplyGnssClock` coverage still passes. Missing: (1) non-wrap elapsed in `projectEpochMilliseconds` (trivial, but documents the baseline); (2) a zero-elapsed case (`ref == now`); (3) any test of main.cpp integration — the readiness gate (`clockIsSynchronized()` true with a valid reference even when system time is below threshold) and the once-only range warning are untestable in the current native setup since `test_build_src = no`. The range guard itself predates the PR, so the delta's untested surface is small, but the reviewer should note the log-once and fallback logic ship without unit coverage.

## Security assessment
No new security surface: the change is internal clock math with no input parsing, no new buffers, no new network behavior, and no secrets touched (the added log line discloses nothing sensitive). The `clockIsSynchronized()` gate becoming GNSS-reference-driven cannot widen authorization (telemetry publish still requires provisioning, WiFi, and valid credentials; TLS will simply fail closed on transport errors if the platform clock is unusable, triggering the existing bounded retry/backoff). No security findings.

## Residual risks
- **49.7-day projection ambiguity** on continuous uptime without a fresh GNSS sentence (telemetry timestamps go stale; backend rejects; self-heals on next GNSS fix). Low likelihood for vehicle-powered devices.
- **Post-2038 TLS**: with `settimeofday` skipped, the 32-bit system clock freezes; mbedTLS cert validation and any time-dependent TLS behavior degrade — expected and documented, but a hard platform limit.
- **Integration paths untested**: `epochMilliseconds()` fallback, readiness gate, and log-once are not covered by the native unit tests; watch the esp32dev build/CI and, if possible, device smoke tests.
