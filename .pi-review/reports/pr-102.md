## Verdict
APPROVE — the freshness math is correct (all-ms units, int64-safe, strict `<` keeps replay age ~5s inside the backend's 60s window), the change is fail-closed and minimal, and it directly fixes the stated root cause (unconditional `RetryLatest` retention of samples that cannot survive the scheduled backoff).

## Summary
PR #102 adds a pure helper `retryKeepsSampleFresh()` in `telemetry_policy.h` and uses it at the two failure exits of `publishFix()` in `hardware/src/main.cpp` (http.begin failure and retryable HTTP responses), so a queued sample is retained only if `sampleAge + scheduledRetryDelay < 55s`. The math is consistent: `fix.timestamp` and `epochMilliseconds()` share one clock, `httpsRetryDelayMs` is read back after `scheduleHttpsRetry()` (so jitter and Retry-After are included), request-level backoff stays active for `Dropped` results (the loop remains gated by `httpsRetryIsPending()`), and the strict inequality plus the 5s gap between the 55s firmware margin and the backend's 60s acceptance window (`telemetryPayload.ts:66`) make backend-rejected stale replays impossible. The 429-without-Retry-After fallback (60s) and Retry-After ≥ 55s necessarily drop — correct per the stated policy. No BLOCKER or MAJOR issues found; remaining findings are MINOR/NIT.

## Findings
- [MINOR] hardware/include/telemetry_policy.h:152-163 (`retryKeepsSampleFresh`) — future-timestamped samples are always dropped (`ageMs < 0 → false`), but the backend contract accepts timestamps up to `now + 10_000` (`backend/src/services/telemetryPayload.ts:66-68`). In a clock-skew scenario (clock corrected backward between capture and a failed first attempt) a replayable sample is discarded even though the backend would accept it. This is clearly deliberate (the new test asserts `(now+1, now, 1000)` → false) and fail-closed; the only cost is rare data loss on the retry path. Suggest documenting the tradeoff in a comment next to the function (e.g., why the device is stricter than the backend's +10s window).
- [NIT] hardware/test/test_telemetry_policy/test_main.cpp:88-100 — the early-return branch `ageMs >= freshnessMarginMs` (sample already stale at check time) is never exercised, and the exact-boundary equality `age + delay == margin` (strict `<` → drop at exactly 55s, e.g. age 25000 + delay 30000) is untested. Add `retryKeepsSampleFresh(now - 55000, now, 0, margin)` → false and `retryKeepsSampleFresh(now - 25000, now, 30000, margin)` → false.
- [NIT] hardware/test/test_telemetry_policy/test_main.cpp:89-99 — the test hard-codes `margin = 55000` instead of sharing `TELEMETRY_FRESHNESS_MARGIN_MS` (it lives in main.cpp's anonymous namespace, so it isn't visible to the test). If the constant in main.cpp changes, the unit test won't catch a drift between the retry check and the `newestFreshFix` gate. `backend/src/securityConfig.test.ts:310` pins the constant's existence but not its consistency with the retry logic.
- [NIT] hardware/src/main.cpp:972-981 (publisher loop) — samples now dropped by the freshness check are counted as `rejectedFixes` (`recordPublishResult(false)`), whereas before they stayed queued and were later counted as queue `staleDrops` by `dropOlderThan`. Operators reading the diagnostics counters will see the drop bucket shift. Intentional, but worth a comment or release note.
- [NIT] hardware/src/main.cpp:705-709, 776-782 — correctness depends on the call order `scheduleHttpsRetry()` → `retryKeepsSampleFresh(..., httpsRetryDelayMs, ...)` (the check must read the *actual* scheduled delay, including jitter and Retry-After). The ordering is correct today, but it is subtle and uncommented; a future refactor could silently pass a stale or smaller delay. Suggest a brief comment stating the dependency.

## Test assessment
The new pure-function test `test_retry_retains_only_samples_that_can_stay_fresh` covers the core matrix: young sample retained (age 0, delay 30s), boundary-adjacent retained (age 20s + 30s = 50s), long delay dropped (60s), accumulated age dropped (30s + 30s = 60s), and future timestamp dropped. All five assertions are arithmetically correct against the function. Missing: the already-stale-at-check branch (`age >= margin`), the exact `age + delay == margin` strict-boundary case, zero-delay behavior, and any wiring-level test of `publishFix` (main.cpp is not compiled in the native test env, so the ordering requirement and the constant wiring are verified only by review; `securityConfig.test.ts` covers the constant's existence). No regression risk: retained samples behave exactly as before (replayed when the backoff expires, re-gated by `newestFreshFix`), so no stale sample can be replayed.

## Security assessment
No new attack surface: the change adds pure int64 arithmetic (no overflow — epoch-ms values are ~1.7e12 and differences are bounded by the clock-sanity guard `clockIsSynchronized()`), introduces no parsing or buffers, and leaves auth, TLS, and payload construction untouched. The behavior is fail-closed (uncertain freshness → drop rather than replay), and future/overshoot timestamps are never sent on retry.

## Questions for author
- Was the backend's `now + 10_000` future-tolerance considered when choosing to drop future-timestamped samples on retry? Fail-closed is defensible, but the asymmetry (device drops what the backend would accept) deserves a comment.
- Should the `rejectedFixes` vs `staleDrops` accounting shift for freshness drops be documented for operators?
- Any plan to extract the 55000 constant to a shared header so the unit test and `publishFix` can't drift?

## Residual risks
- Clock-step between `millis()` (backoff window) and epoch-ms (age) is handled fail-closed: a forward step makes the sample look older and the gate drops it at the next attempt; a backward step only makes it younger. No stale replay possible.
- 429 with an HTTP-date `Retry-After` (not delta-seconds) parses to 0 → 60s fallback → sample dropped even for young samples. Pre-existing parsing limitation; the Eki backend emits delta-seconds.
- Polling granularity after backoff expiry (~1ms when drained) adds ≤2ms to actual replay age; the 5s guard band against the backend's 60s window absorbs this.
- CI (hardware native tests + esp32dev build, per PR body) should be re-run after merge; watch the new unit test under the native env and the two changed `publishFix` exits in the esp32dev build.
- Overlapping open PRs touch `hardware/src/main.cpp`; merge-order conflicts are possible but the changed hunks are localized.
