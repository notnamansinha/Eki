## Verdict

APPROVE — The PR fixes the stated root cause (#78: the diagnostic interval was recorded *before* the send, so failed sends suppressed diagnostics for 5 minutes), adds bounded 5–60s exponential backoff with reset-on-success, retains the 401/403 latch, and the change is minimal, consistent with existing retry patterns, and backed by a correct pure-function test.

## Summary

Base code recorded `remoteDiagnosticAttempted = true; lastRemoteDiagnosticAt = millis();` before the payload-size check and `http.begin()` (base main.cpp:821-822), so any failed attempt (transport, init, oversized payload) still armed the 5-minute interval and stalled diagnostics for 5 minutes — the root cause of #78. The PR moves interval recording into a `2xx`-only branch, adds `scheduleRemoteDiagnosticRetry()` for init/transport/oversized/non-2xx failures with a deterministic 5→60s exponential backoff that resets on success, and keeps 401/403 latching with an explicit early return so credential faults are never retried. Retry gating lives in `remoteDiagnosticIsDue()`, so the publisher loop cannot spin tight HTTP retry loops. Overall quality is good; only nits (magic numbers, no jitter, missing state-machine tests).

## Findings

- [NIT] hardware/include/telemetry_policy.h:27-31 — Magic numbers `5000` and exponent cap `4` in `diagnosticRetryDelayMs`. Works correctly (`5000UL << 4 = 80000` → capped to 60000, no uint32 overflow, `consecutiveFailures-1` can't underflow since 0 is short-circuited), but a `DIAGNOSTIC_RETRY_BASE_MS` constant would mirror `HTTPS_RETRY_BASE_MS`/`HTTPS_RETRY_MAX_MS` style.
- [MINOR] hardware/include/telemetry_policy.h:27-31 — Deterministic backoff with **no jitter**. The HTTPS path deliberately jitters (`scheduleHttpsRetry` comment, main.cpp:373-375: "Per-device jitter prevents a recovering hotspot/backend from receiving a synchronized retry wave from the whole fleet"), but all devices failing simultaneously will now retry diagnostics in lockstep at 5/10/20/40/60s. Suggest a per-device random offset or `esp_random()`-based jitter within each bucket, or confirm a synchronized wave is acceptable for the diagnostics endpoint.
- [MINOR] hardware/src/main.cpp:871-878 — All non-2xx (except 401/403), including 3xx and unrecoverable 4xx (400/404/422), are retried indefinitely with a 60s cap; there is no max-attempt circuit breaker. This matches the PR description ("other failed sends") and mirrors the HTTPS retry pattern, but a permanently misconfigured endpoint produces an eternal once-per-minute retry plus a serial log line. Consider a retry-count ceiling or log escalation.
- [NIT] hardware/src/main.cpp:803-809 vs 783-790 — If WiFi drops/clock desyncs during a retry window, the guard early-returns without resetting the backoff timer; if the window elapses during the outage, the first send after restore fires immediately, slightly compressing the backoff. Not a tight loop (guard returns before any HTTP work) and arguably desirable — just be aware of the behavior.
- [NIT] hardware/test/test_telemetry_policy/test_main.cpp:48-56 — No assertion for `diagnosticRetryDelayMs(3) == 20000`; the mid-series value is skipped (0/1/2/4/5/100 covered). Cosmetic; bounds, doubling, cap, and saturation are all covered.

Verified correct (no findings):

- **2xx definition**: `responseCode >= 200 && responseCode < 300` (main.cpp:871) — includes 204, excludes 3xx (3xx is retried; HTTPClient POST doesn't auto-follow redirects, so this is a safe, if slightly wasteful, default).

## Security assessment

Fail-closed posture is preserved and strengthened: diagnostics only send when provisioned, WiFi-connected, clock-synced, and not in a credential-fault state (main.cpp:803-809); 401/403 still latch the credential fault and disconnect WiFi rather than retrying (fail-closed on bad credentials); the oversized-payload guard is retained (and now correctly retried instead of being silently counted as a "sent" diagnostic); the Authorization header and endpoint are unchanged; no new input parsing or buffer writes are introduced; the backoff arithmetic is overflow-safe. No new attack surface found.

## Residual risks

- The retry/latch state machine in `main.cpp` has no unit tests; only the pure backoff function is tested. A regression in `remoteDiagnosticIsDue()`/`scheduleRemoteDiagnosticRetry()` would only surface in the native build compile or field behavior.
- Unbounded retries (capped at 60s spacing) against an endpoint that persistently returns 4xx/3xx — perpetual once-a-minute POST + log spam until success or reboot.
- Deterministic retry timing across the fleet could synchronize load on the diagnostics endpoint after a shared outage (mitigatable with jitter).
- Several open PRs touch `hardware/src/main.cpp`; merge-order conflicts are possible. This review covers only the PR #101 diff as specified.
- Post-reconnect behavior (immediate send if backoff window elapsed during an outage) slightly weakens backoff spacing in that one scenario — no tight loop.
