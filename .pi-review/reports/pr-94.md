## Verdict
**APPROVE** — the implementation correctly and minimally implements all four claimed behaviors (sub-metre jitter filter, time-based 20 fps commit cap, minimum-movement render gate, guaranteed final commit) with sound edge-case handling; only gaps are absent tests and a couple of latent edges that no current caller triggers.

## Summary
PR #94 rewrites `useSmoothPosition.ts` so that (1) targets within 1 m of the last accepted position are ignored (jitter rejection), (2) React `setPosition` commits are throttled by wall-time to ≥50 ms apart (≤20 fps) and additionally gated on ≥0.5 m of movement from the last rendered point, while the rAF interpolation loop still runs every frame updating `currentRef`, and (3) the exact target is always committed at `progress === 1`. The logic is traced-correct against the base version: no drift, monotonic timestamps, final position guaranteed, reduced-motion path preserved, and both current callers (`PassengerMap`/`DriverMap`) use the default 800 ms duration, so the short-duration edge is latent. Quality is good (small, readable, module-level constants), but no tests were added for any of the new behavior.

## Findings
- [MINOR] frontend/src/hooks/useSmoothPosition.ts:36-45 — No tests for the new throttling/threshold logic. The PR body claims `vitest run src` (75 tests) passes, but none of those tests exercise this hook (no `useSmoothPosition.test.ts` exists; grep found zero references to the hook in test files). The 50 ms cap, the `progress === 1` final commit, the 1 m jitter threshold, the 0.5 m render threshold, reduced-motion, and null-target paths are all untested timing-sensitive logic. Suggest adding a hook test with a fake rAF/clock (see Test assessment).
- [MINOR] useSmoothPosition.ts:20-21,35 — `durationMs < RENDER_INTERVAL_MS` (e.g., 30 ms) means intermediate frames are never committed: `renderDue` stays false until `progress === 1`, so the marker jumps straight to the final target instead of animating (base code committed every frame). No current caller passes a custom duration (both call sites use the default 800 ms — PassengerMap.tsx:83, DriverMap.tsx:156), so this is latent, but the hook is exported API. Consider making the throttle relative to duration (`Math.min(RENDER_INTERVAL_MS, durationMs / 2)`) or documenting the constraint.
- [MINOR] useSmoothPosition.ts:46-49 — Pre-existing race slightly amplified: `let frame = 0` means a cleanup that runs before the first rAF fires calls `cancelAnimationFrame(0)` (a no-op), so the stale animation closure keeps scheduling its own frames and can run concurrently with a replacement effect's loop (two independent `lastRenderedAt`/`renderedRef` closures → interleaved commits toward two targets for up to `durationMs`). Requires a target change within ~16 ms of effect start (RTDB `onValue` updates are seconds apart), so likelihood is negligible; base code had the same pattern. Suggested fix: `if (frame) cancelAnimationFrame(frame)` or a `cancelled` flag checked inside `animate`.
- [MINOR] useSmoothPosition.ts:34-38 — First commit of each animation is delayed ≥50 ms (marker rests ~3 frames before moving) and, for slow creep (<1 m per update), the marker can pause and restart when a jittery update cancels an in-flight animation. Both are intentional consequences of the throttle/jitter design and sub-pixel at the map's zoom levels (see below), but a brief comment in the code explaining the design intent would help future maintainers.
- [NIT] useSmoothPosition.ts:4-6 — `MIN_TARGET_CHANGE_METERS`/`MIN_RENDER_CHANGE_METERS`/`RENDER_INTERVAL_MS` are undocumented magic numbers. At the maps' zooms (PassengerMap default 15, zoom-to 16; DriverMap default 14 ≈ 8.8 m/px at lat 23), 0.5-1 m is far sub-pixel, so no stepping artifacts; at zoom ≥18 (not used here) 0.5 m ≈ 0.9 px and the 20 fps commits would be just-visible steps. Fine for current usage; a one-line comment tying thresholds to zoom scale would prevent misuse.

## Test assessment
No tests were added or updated; the hook has zero existing test coverage and the changed file is entirely untested logic. Missing cases that should be added:
- Throttle: with a mock rAF advancing time, assert `setPosition` is called at most every 50 ms (≤20 fps) over an 800 ms animation, and that `currentRef` still advances every frame.
- Final commit: after the last frame (`progress === 1`), `position === target` exactly; also simulate a backgrounded tab (rAF gap > duration) and assert the resume frame commits the final target.
- Jitter threshold: new target <1 m from current position → no new animation, no state change; creeping targets (0.6 m/update) eventually trigger an animation once cumulative distance ≥1 m.
- Render threshold: slow animation where per-commit movement <0.5 m → commits skipped until the 0.5 m threshold is crossed.
- Reduced-motion path: target committed immediately, sub-metre jitter still filtered.
- Null target and unmount mid-animation: rAF cancelled, returns null, refs reset.
- Short-duration edge (`durationMs < 50`): document or assert the jump-to-final behavior.

## Security assessment
No security surface is affected: this is a client-side rendering throttle. Inputs (`target` lat/lng) flow from RTDB bus snapshots already gated by `hasValidBusCoordinates` (PassengerMap.tsx) before reaching the hook; `getDistanceMeters` is pure arithmetic over those finite numbers with no side effects, secrets, or authorization logic touched. No new risk introduced.

- Was a `durationMs` of less than 50 ms ever used or intended for any caller?

## Residual risks
- The pre-existing `cancelAnimationFrame(0)` race could, in a pathological rapid-target-change scenario, briefly run two animation loops; watch for any reported marker flicker after merge.
- The marker now rests up to ~1-1.5 m from the true bus position at steady state (jitter filter + commit lag); if any future UI does metre-precision proximity checks against the smooth position, it must use the raw target instead.
- No automated coverage for the timing logic, so CI passing (75 tests) does not validate this change; a regression (e.g., removing the `progress === 1` bypass) would silently reintroduce the freeze-at-stale-point bug.
- Constants are hardcoded; if the maps ever add high-zoom (≥18) or high-DPI density modes, the 0.5 m render threshold may need to become zoom-relative.
