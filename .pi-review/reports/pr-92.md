## Verdict
COMMENT — the implementation is correct, well-tested, and preserves cancellation, but the new `AbortSignal.any` dependency raises the browser baseline (Safari 17.4+/Chrome 116+) with no fallback, and a few error-path tests are missing.

## Summary
PR #92 adds a single `apiRequest` client (10s timeout, URL normalization, centralized HTTP/network/timeout error handling) and migrates the driver page plus five admin components to it, preserving both existing AbortController flows. It fixes the root cause of #34 for the migrated sites: requests can no longer hang forever and error handling is consistent. Quality is high — minimal diffs, server error messages now surface where the base code showed generic text, and the tests exercise success, timeout, HTTP error, cancellation, and malformed-JSON paths — but `AbortSignal.any` and a couple of unhandled response shapes deserve a second look.

## Findings
- [MAJOR] frontend/src/lib/apiClient.ts:34-36 — `AbortSignal.any` requires Safari 17.4+ / Chrome 116+ / Firefox 120+; on older browsers every `apiRequest` throws `TypeError: AbortSignal.any is not a function` and all driver/admin API calls fail. The repo already relies on `AbortSignal.timeout` (iOS 15.4+, March 2022) in five other files (feedback/page.tsx:277, FeedbackModal.tsx:143, MessagingPanel.tsx:184, useAuth.ts:149, useSettings.ts:147), so iOS 15.4–17.3 users who work today would break after this PR; no polyfill or browserslist exists in the repo. Suggest replacing `AbortSignal.any` with a small helper that links the caller's controller and the timeout controller (each aborts a shared controller), or a feature-detect fallback.
- [MINOR] frontend/src/lib/apiClient.ts:41-46 — a 2xx response with no JSON body (204 or empty 200) makes `response.json()` throw and, because `response.ok` is true, the SyntaxError is rethrown to callers. No currently migrated endpoint returns 204 (verified against backend/src/routes/shifts.ts, fleet.ts, polyline.ts, places.ts), so no live regression — but the client is brittle for future endpoints and this path is untested. Suggest `if (response.status === 204) return undefined as T;` before parsing.
- [MINOR] frontend/src/lib/apiClient.ts:47-48 — `new Error(result.error || …)` assumes `error` is a string; a non-string error field (e.g. `{ error: {...} }` or a number) renders as "[object Object]" in the UI. Current backend always sends strings, so this is defensive only — guard with `typeof result.error === "string"`.
- [MINOR] frontend/src/lib/apiClient.test.ts — missing failure-path coverage: (a) network failure (fetch rejects with TypeError) propagation; (b) HTTP error with a non-JSON/empty body, which is the branch at apiClient.ts:43-45 + `fallbackError (HTTP status)` at :48; (c) 204/no-content (explicitly requested in the review focus); (d) missing env var (only invalid values are tested); (e) timeout combined with a caller signal (the `AbortSignal.any` path is only exercised by the cancellation test); (f) passing an already-aborted signal.
- [NIT] frontend/src/lib/apiClient.ts:9,23 — a present-but-invalid `NEXT_PUBLIC_BACKEND_URL` (wrong scheme, query string, credentials) surfaces as "Backend service is not configured.", which is misleading; consider "Backend URL is invalid or not configured.".
- [NOTE] Partial centralization — 8+ backend call sites remain on raw fetch with divergent handling: feedback/page.tsx:267, FeedbackModal.tsx:114, MessagingPanel.tsx:159, useAuth.ts:141, useSettings.ts:135, DriverMap.tsx:73 (delay sync, errors only go to console.error), AccountTab.tsx:20, PassengerBoardingView.tsx:78. Issue #34's centralization goal is only partially met; confirm the remaining sites are tracked as follow-ups so the two patterns don't drift.
- [NIT] frontend/src/app/driver/page.tsx:166-176 (boarding code) and RouteManagementPanel.tsx:57-68 — the generic timeout message ("The request timed out. Please try again.") supersedes the per-site fallbacks. Acceptable (arguably better), but note that a timed-out non-idempotent mutation (route create/save, shift start) may still complete server-side; a user retry on route create then hits 409 "already exists" (backend/src/routes/polyline.ts:164-166). Low probability, no code change required.

## Test assessment
Tests genuinely exercise the new behavior: success + backend URL joining (apiClient.test.ts:11-21), server error message surfaced (23-29), trailing-slash normalization and unsafe-URL rejection (31-49), caller cancellation with AbortError propagation (51-63), timeout during the body read including the friendly-message rewrap (65-84), and SyntaxError on malformed JSON from a 200 (86-94). Gaps: network-error propagation, HTTP error with non-JSON body, 204/no-content (would currently throw SyntaxError), missing-env, timeout combined with a caller signal, and pre-aborted signal — see Finding 4. Note the test for the timeout path mocks `AbortSignal.timeout`, so the real 10s auto-abort is untested by necessity (fine).

## Security assessment
The change is fail-closed: `configuredBackendUrl` restricts to http/https, rejects embedded credentials, query strings, and hashes (apiClient.ts:11-20), preventing credential smuggling and `javascript:`-style backends; a missing/invalid URL throws before any fetch. The 10s abort prevents dangling connections and slow-loris-style client hangs. No secrets are added, the auth flow is untouched (Bearer tokens still attached per call site), and the server error strings surfaced to the UI match base behavior. No new authorization surface introduced.

## Residual risks
- Older-browser crash (TypeError on `AbortSignal.any`) would take down every migrated API call — the main thing to confirm before merge.
- Client-side timeout on non-idempotent mutations may race server-side completion; retries can surface 409s. Watch driver shift-start and route save flows after deploy.
- Any future endpoint returning an empty 2xx will throw SyntaxError through `apiRequest` until 204 handling is added.
- Two API patterns now coexist (migrated vs. raw fetch); without follow-up migration the inconsistency persists. CI only runs lint + vitest (`npm run test`), so browser-only failures won't be caught — worth a manual check on a Safari 17.3 device if that matters.
