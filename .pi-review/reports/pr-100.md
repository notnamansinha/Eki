## Review

### Verdict
**REQUEST CHANGES** — the teardown/reattach and backoff-reset logic is correct and leak-free, but the retry is unbounded in attempt count (contradicting the PR's "bounded" claim) and the store-level recovery behavior — the actual fix — has zero test coverage.

### Summary
PR #100 makes `liveBusStore` recover from terminal RTDB listener errors: on error it detaches the dead listener, clears the cache, notifies subscribers (invalidation + error), and reattaches on an exponential backoff (1s → 30s cap) that resets after any authoritative snapshot and is cancelled when the last subscriber leaves. The teardown/reattach logic is sound — no duplicate listeners, no timer/listener leaks, idempotent on repeated errors — and the backoff-reset is correctly gated on authoritative (listener-source) snapshots. The main gaps: the retry loop never gives up while subscribers exist (delay-bounded but count-unbounded), and the only new test covers the delay schedule, not any of the recovery behavior the PR is about.

### Findings
- [MAJOR] frontend/src/lib/liveBusStore.ts (head, error callback ~L86–92 and catch ~L98–104) — Retry is **not bounded in attempts**. Every failure schedules the next retry (`if (subscribers.size > 0 && !retryTimer)` → `liveBusRetryDelayMs(retryAttempt++)` → new `setTimeout`); there is no max-attempt counter or give-up path. Only the *delay* is capped (30s, verified in `liveBusRetry.ts:3–7`). The PR description promises "one bounded exponential retry", and the review lane asks to verify max attempts. For a permanent error (e.g., security-rules permission denied) this spins forever — one `error` callback + `invalidation` notification per subscriber every ~30s, indefinitely. It is *not* a tight loop (min 1s spacing, 30s cap) and it does die with the last subscriber, and unbounded retry is arguably desirable for the likely root cause (an auth/permission race per `authState.ts`), so this is a contract/behavior mismatch rather than a functional blocker. Fix: either add a max-attempt cap (e.g., give up after N consecutive failures and only retry on next subscribe/`connectionGeneration` change), or confirm the intent and fix the description.
- [MAJOR] frontend/src/lib/liveBusRetry.test.ts:1–10 — No tests for the store's recovery logic. The only new test exercises the pure delay function. The behaviors this PR is about — terminal error clears cache + notifies invalidation/error, listener detached, exactly one retry scheduled; retry success resets backoff to 0; last subscriber leaving mid-retry cancels the timer and prevents reattach; repeated errors are idempotent with no duplicate listeners — are all untested. The pre-existing `liveBusStore.test.ts` only tests `liveBusSnapshot` helpers and never imports `liveBusStore.ts`, so the PR's "frontend 76 passed" does not cover any of the new code paths. Add store-level tests (mock `firebase/database`'s `onValue`) for terminal error, retry success, and subscriber-leave-mid-retry.
- [MINOR] frontend/src/lib/liveBusStore.ts (head ~L87, ~L99) — `retryAttempt` increments without bound during a long outage (at 30s cadence ≈ 2,880/day; no overflow risk since `2 ** exponent` is capped at 32 by `Math.min(attempt, 5)`). Cosmetic, but capping `retryAttempt` at 5 would keep the state tidy.
- [NIT] frontend/src/lib/liveBusStore.ts (head ~L95–104) — The catch block duplicates the error-callback retry-scheduling block (same `if`/delay/`setTimeout` shape). Extract a small `scheduleRetry()` helper. Note the catch is effectively unreachable today (`waitForAuth` in `authState.ts` never rejects) but is good defensive coverage.
- [NIT] frontend/src/lib/liveBusStore.ts (head ~L96–97) — If a subscriber's `error` handler throws inside the catch block, `ensureListener()`'s promise rejects and `void ensureListener()` (called at L90/102 and in `subscribeLiveBuses`) becomes an unhandled rejection. All three current callers only `console.warn` (`useActiveBuses.ts:44–46`, `passenger/page.tsx:131–133`, `PassengerMap.tsx:367–369`), so low practical risk; wrapping the error fan-out in a guard or using `void ensureListener().catch(...)` would harden it.

Verified-correct aspects (no findings):
- Teardown/reattach: error callback calls `unsubscribe?.()` then nulls it — safe/idempotent (Firebase RTDB auto-removes the listener before invoking the cancel callback, and re-unsubscribing a removed listener is a no-op). `ensureListener` guards on `unsubscribe || starting || retryTimer || subscribers.size === 0` (head L65), so no duplicate listeners; repeated errors take the same path deterministically.
- Cancel-on-leave: teardown (head L127–131) clears `retryTimer` and resets `retryAttempt`; an in-flight `ensureListener` (timer already fired) re-checks `subscribers.size === 0` after `waitForAuth` (head L69) and returns without attaching. No timer or listener leak.
- Backoff reset: `retryAttempt = 0` only in the `onValue` success callback (head L72), which per `liveBusDelivery.ts` (`isAuthoritativeLiveBusDelivery`) is the only authoritative source; null/empty snapshots still count as authoritative DB reads, which is correct.
- Backoff schedule: 1s, 2s, 4s, 8s, 16s, 30s cap — exponential with sane bounds; matches the unit test exactly (attempts 0–5 and 20 → `[1000,2000,4000,8000,16000,30000,30000]`).
- Callers: all handle `null` (invalidation) deliveries and errors gracefully; `markSnapshotReceived` only fires for `"listener"` source, so the reconnect indicator stays visible until a real snapshot arrives after recovery. `useRTDBResume`'s `invalidateLiveBusCache()`/`connectionGeneration` re-subscribe coexist cleanly with the retry timer (teardown clears it).

### Test assessment
The one added test (`liveBusRetryDelayMs`) is correct and covers the exponential ramp plus the 30s cap (attempts 5 and 20), but it does not exercise any of the PR's actual behavior. Missing cases: (1) terminal listener error → cache cleared, subscribers get `null` (invalidation) then `error`, listener detached, exactly one retry scheduled; (2) retry success → `retryAttempt` reset to 0 and backoff restarts; (3) last subscriber leaves mid-retry → timer cancelled, `ensureListener` does not reattach after pending auth; (4) repeated errors → no duplicate listeners/timers; (5) negative/non-integer `attempt` input. No existing test covers `liveBusStore.ts` at all, so the fix's core logic is entirely untested.

### Security assessment
No new exposure: the retry reattaches to the same auth-gated `activeBuses` path under the existing RTDB rules, using the same (post-auth) session — fail-closed, no data is served before auth. The error path clears cached data rather than leaking stale fleet state. No secrets, user input, or buffer-boundary concerns; `snapshot.val()` casting is unchanged from base. The only marginal impact is a modest increase in RTDB read frequency on persistent errors (up to 1 query per 30s per open subscription), which is within normal RTDB usage patterns.

### Questions for author
- Is the retry intended to be unbounded in count (retry forever at ≤30s intervals while subscribers exist)? If a max-attempt policy was intended, what is it — and should error notifications be throttled to avoid a `console.warn` per subscriber every 30s during a persistent outage?
- Any plan to add store-level tests with a mocked `onValue` (terminal error, retry success, subscriber-leave mid-retry)? The current test file covers only the delay function.
- Was the "bounded" wording in the PR description meant to refer to the delay cap only?

### Residual risks
- Persistent permission-denied or cancelled-listener errors will retry indefinitely and repeatedly fire subscriber error/invalidation callbacks every ~30s; watch production logs and RTDB read volume after merge.
- If `waitForAuth` never resolves (auth never fires), the listener never attaches — pre-existing behavior, unchanged by this PR, but the retry loop also can't recover it.
- The head branch was not present locally; line numbers are from the diff-reconstructed head against `origin/main`. CI (eslint/vitest/tsc) should confirm the merged state.
- Subscriber churn racing the retry timer (join/leave exactly as the timer fires) is handled by the guards but is untested — the most likely source of a future flake.
