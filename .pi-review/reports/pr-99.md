## Verdict

## Summary
PR #99 replaces the lone `gps.location.age() > 5000` literal with a single shared constant `GNSS_FIX_MAX_AGE_MS = 5000` (`hardware/src/main.cpp:34`) and adds freshness gates for HDOP, speed, and course inside `currentFix()`, so a valid-but-stale optional field now invalidates the whole fix while genuinely absent speed/course still fall through to the zero/default path. This directly fixes the root cause of #71: the base code only aged location, so stale-but-valid HDOP/speed/course were published as fresh. The code is correct and minimal, but the changed behavior is entirely untested, and the fail-closed rejection cascades into the fix-loss/uncertain-sample path in `evaluateTelemetry()`.

## Findings
- [MAJOR] hardware/src/main.cpp:857-861 — No tests cover any of the new freshness logic. `[env:native]` sets `test_build_src = no` (platformio.ini), so `currentFix()` — which lives in `src/main.cpp` and depends on the global `gps` object — is not even compiled by the test suites. The "22 tests passed" claim covers only pure policy functions (`shouldPublishFix`, the queue, reset stats) in `hardware/test/test_telemetry_policy/test_main.cpp` and `test/test_reset_stats/test_main.cpp`; `grep` for gps/hdop/course in `test/` finds nothing. Fix: extract the freshness predicate into a testable pure function under `hardware/include/` (or a TinyGPSPlus-stubbing harness) and add cases: stale location, valid-but-stale HDOP, present+stale speed, present+stale course, absent speed/course with fresh position, exactly-5000ms boundary, HDOP > 4.0 with fresh age.
- [MINOR] hardware/src/main.cpp:856-863 — Whole-fix rejection (rather than field-level zeroing) on a stale optional field cascades into the loss path: `evaluateTelemetry()` (main.cpp:912-930) treats the fix as lost, logs "Trustworthy fix lost", and enqueues an uncertain sample with the last known position and speed 0 whenever a receiver's speed/course refresh lags position by >5s. That churn (and the downstream "stationary" inference from speed-0 uncertain samples) is a behavior change from the base, where a fresh position with stale speed/course was still published. The PR description says this is intended (fail-closed), but confirm it was considered end-to-end; an alternative is zeroing just the stale field.
- [MINOR] hardware/src/main.cpp:860 — The HDOP freshness gate assumes the receiver refreshes HDOP (GGA/GSA) within 5s of the position fix. The base already required `hdop.isValid()`, so GGA/GSA must flow, but a receiver with a slower GGA cadence or duty-cycled sentences would now report continuous fix loss even with fresh RMC positions. Verify the deployed module's default sentence cadence (Serial2 @ 9600, main.cpp:1079) against this horizon.
- [NIT] hardware/src/main.cpp:857 — Boundary semantics: `age() > 5000` accepts a fix at exactly 5.0s and rejects from 5001ms (ms granularity). This is identical to the pre-existing literal's semantics (no regression), but if a strict "5s or older" cutoff is wanted, `>=` would be the change. No off-by-one introduced.
- [NIT] Validation claims in the PR body (`22 tests`, esp32dev build) could not be reproduced in this workspace per the shared-build constraint; static checks only. Regardless, the tests do not exercise the changed lines, so a passing suite does not validate this PR's behavior.

## Test assessment
No tests were added or updated; the only changed file is `hardware/src/main.cpp`. Because `test_build_src = no`, the native environment compiles only the test files plus `include/` headers — `currentFix()` and its new gates are dead code from the tests' perspective. Missing cases: stale-but-valid HDOP; present+stale speed; present+stale course; boundary at exactly 5000ms; fresh location with genuinely absent speed/course (zero path); HDOP value gate with fresh age; and millis() wraparound. The PR's 22 passing tests are orthogonal to this change.

## Security assessment
No security surface is touched: no authorization, secrets, buffers, or network paths are modified. The change is data-quality gating, and its direction is fail-closed — it rejects rather than emits potentially stale telemetry, which is the safer choice for a position-reporting device. `age()` is only invoked on fields already validated by short-circuited `isValid()` checks, so there is no path where a sentinel (`ULONG_MAX` for invalid fields in TinyGPSPlus 1.1.0) leaks into the comparison.

## Questions for author
- Was whole-fix rejection (vs. zeroing only the stale field) deliberately chosen knowing it routes through the "Trustworthy fix lost" path and emits uncertain speed-0 samples at the last known position downstream?
- Is the deployed GPS module's default sentence mix guaranteed to refresh HDOP and speed/course at the same cadence as position (i.e., never a lag >5s in normal operation)? Any field data or unit test?
- Boundary: keep `>` (accept exactly 5000ms) or switch to `>=` for a strict cutoff?
- Will native coverage be added for the freshness predicate (requires extracting it into `hardware/include/` since `test_build_src = no`)?

## Residual risks
- Receivers whose HDOP/speed/course refresh slower than position will now trigger repeated fix-loss churn and a stream of uncertain samples; backend consumers interpreting speed-0 uncertain samples as "device stopped" could see false stationary episodes.
- The new gates are untested in CI, so a future refactor could silently revert them without any test failing.
- If the module's NMEA cadence or sentence mix changes in a future board revision (e.g., GGA-only or duty-cycled output), the 5s horizon may need tuning; there is no config knob today.
- The claimed 22-test/build validation is unverifiable from this workspace; watch CI for the esp32dev build once merged.
