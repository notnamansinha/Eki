## Verdict
REQUEST CHANGES — the single-tab state machine is sound and does fix #35, but the origin-global, last-writer-wins shift state can still trigger the exact mid-shift reload the PR is meant to prevent (multi-tab case), several paths leave the waiting worker pending indefinitely with no TTL or recovery, and none of the new logic is tested.

## Summary
PR #93 removes `self.skipWaiting()` from sw.js and replaces unconditional activation with a localStorage-backed shift-state gate: `/driver` publishes `checking`/`active`/`inactive` from React effects plus the RTDB `activeBuses` listener, and `ServiceWorkerRegistrar` posts `SKIP_WAITING` only when the state is neither `checking` nor `active`. The single-tab happy path is correct — a live shift blocks activation, and a shift-end event activates the waiting worker via the event listener. However, the state is a single origin-global scalar with last-writer-wins semantics and no cross-tab coordination (no `storage`-event listener, no TTL, no unmount cleanup), so a second driver tab can clobber `active` → `inactive` and reload the mid-shift tab; the RTDB error path leaves state stuck at `checking`; and zero tests cover any of it.

## Findings
- [MAJOR] frontend/src/lib/serviceWorkerUpdate.ts:6-13 + frontend/src/components/ServiceWorkerRegistrar.tsx:38-42,63 + frontend/src/sw.js:163-166 — Multi-tab last-writer-wins can reload a live shift (defeats the fix). The state is one origin-wide localStorage key written independently by every `/driver` tab (page.tsx:59,65,68,74). `setDriverShiftUpdateState` dispatches only a same-window `CustomEvent`; no tab listens for the `storage` event (grep confirms zero listeners). Since `skipWaiting()` is per-registration (not per-tab), any tab whose registrar passes `canActivateServiceWorker()` posts SKIP_WAITING globally, firing `controllerchange` → reload (registrar:44-53) in **every** controlled tab — including a tab mid-shift. A second driver tab (fresh load writes `checking`, then its own `inactive` once its RTDB view shows no shift) can therefore reload the first tab mid-ride. Symmetrically, a stale `active` left by a tab closed mid-shift blocks updates origin-wide — including passenger tabs, because the registrar is mounted in the root layout (frontend/src/app/layout.tsx:55). Suggested fix: make the gate a per-tab count/union (BroadcastChannel or `storage` events + active-tab count), or gate activation on RTDB-authoritative data instead of a single shared scalar; clear the key on unmount and add a TTL.
- [MAJOR] frontend/src/app/driver/page.tsx:58-79,127-133,158-159 — Stuck `checking` state blocks SW updates indefinitely while a tab is open. `checking` is only cleared by the RTDB success callback (`setShiftStatusKnown(true)` at line 133) or the `[busId, selectedRouteIds]` branch flipping to `inactive`. The `onValue` error callback (lines 158-159, pre-existing) never clears the state; for non-retryable listen failures (e.g., permission denied) the RTDB listener is torn down, so `shiftStatusKnown` never becomes true and the tab stays in `checking` for its lifetime. There is no timeout, no TTL, and no re-evaluation on visibilitychange, so a waiting worker can pend forever with the tab open. Suggested fix: in the error callback set `shiftStatusKnown(true)` + `"inactive"` (fail-open on unknown), or add a timer that flips `checking` → `inactive` after N seconds.
- [MAJOR] (PR adds no tests) — The deferral logic is untested end to end. `serviceWorkerUpdate.ts` (null/missing-key and garbage-value handling, event dispatch), the three state effects in page.tsx, the registrar's activation gating, and the sw.js SKIP_WAITING handler have zero coverage; the claimed "75 tests" are the pre-existing suite (10 test files, none importing any changed module — verified by grep). Missing cases are listed in the Test assessment below.
- [MINOR] frontend/src/components/ServiceWorkerRegistrar.tsx:38-42 — Race: shift start during the activation window. `SKIP_WAITING` is posted the moment state is `inactive`; if the driver starts a shift (POST `/api/shifts/start` → RTDB `active`) before the worker finishes activating, `controllerchange` reloads mid-start. The window (SW wake + activate) can be hundreds of ms. Suggested fix: re-check state after a short delay before posting, or have the SW-side handler confirm no `active` write arrived within a grace period.
- [MINOR] frontend/src/lib/serviceWorkerUpdate.ts:7,12 — Un-guarded `window.localStorage` access. `setItem`/`getItem` can throw when storage is blocked (Safari private mode, storage-disabled); a throw inside a React effect (page.tsx:59) crashes the driver page. Wrap both in try/catch (treating read failure as "allow activation" — the current fail-open default).
- [NIT] frontend/src/components/ServiceWorkerRegistrar.tsx:96 — `statechange` posts via `activeRegistration?.waiting` instead of the captured `newWorker` (as the base code did). If `registration.waiting` is momentarily null at `state === "installed"` (spec-timing edge), the SKIP_WAITING is skipped with no retry until the next shift-end event re-reads `registration.waiting` (self-heals, but strictly less robust than the original pattern).
- [NIT] Migration: one-time reload for tabs already open at deploy time. The old page/registrar code posts SKIP_WAITING unconditionally when the new SW installs, so any tab open at deployment (including a mid-shift driver tab) reloads once. Unavoidable with a client-side protocol change, but should be watched during rollout.

## Test assessment
No tests were added or updated. Verified missing cases:
1. `canActivateServiceWorker()`: missing key (null), `"checking"`, `"active"`, `"inactive"`, and garbage/stale values.
2. `setDriverShiftUpdateState()`: writes the key and dispatches `DRIVER_SHIFT_UPDATE_EVENT` (and that the write fires cross-tab `storage` events — which nobody listens to; a test would surface the multi-tab gap).
3. State transitions in page.tsx: mount → `checking`; no bus/route → `inactive`; route selected → `checking` until RTDB resolves; RTDB `active` → `active`; RTDB inactive/null → `inactive`; **error callback → stuck `checking`** (currently untested because uncovered).
4. Registrar: no postMessage while `checking`/`active`; postMessage on shift-end event; updatefound/installed path; cleanup removes the event listener.
5. sw.js: SKIP_WAITING message handler and no-op behavior when the worker is already active (no SW test harness exists in the repo).
Given the state machine is the entire point of the PR and it embeds cross-tab semantics, the absence of tests for the deferral logic is the main coverage gap.

## Security assessment
No authorization, secret, input-validation, or buffer-bound concerns: the changed code is client-side lifecycle plumbing with no data handling, and `SKIP_WAITING` over `postMessage` is same-origin only. Two availability-related notes: the shift state is per-origin, not per-user, so one driver's mid-shift tab state blocks SW updates for everyone on that browser/device (including passenger views), and the fail-open direction on missing state (activation proceeds) means the system degrades to the old behavior rather than failing closed — acceptable here since a stuck update is benign versus a mid-shift reload.

## Questions for author
- Should activation be gated on RTDB-authoritative state rather than a per-tab scalar, or at minimum made multi-tab-aware (storage-event listener or BroadcastChannel with an active-tab count)?
- What is the intended recovery when the RTDB listener error callback fires (permission/network)? Should `checking` expire after a timeout?
- Why is the state not cleared or expired on page unmount / `beforeunload`, given the Back button unmounts `/driver` mid-shift (page.tsx Back-button FAB)?
- Is a reload of a non-shift tab acceptable when a shift ends (the current behavior reloads every controlled tab on activation)? If not, should only the driver tab reload?
- Was the `registration.waiting`-vs-`newWorker` change intentional, and is the single-tab happy path covered by any manual test (e.g., deploy v2 while a shift is live, end the shift, confirm activation)?

## Residual risks
- Multi-tab: a second `/driver` tab writing `inactive` can activate the worker and reload a tab mid-shift — the exact #35 symptom, reproduced after merge in multi-tab usage.
- Stuck states (`checking` after listen errors, stale `active` after mid-shift close/unmount) block all SW updates origin-wide until the next `/driver` visit; passengers are affected since the registrar is in the root layout.
- One-time mid-shift reload for tabs open at deploy time (old client posts SKIP_WAITING unconditionally); watch the first rollout.
- Shift-start-during-activation race can interrupt a shift start.
- Watch in CI: if future PRs add tests for `serviceWorkerUpdate`, ensure a jsdom/happy-dom environment that supports `localStorage` + `CustomEvent`; the sw.js handler remains untestable without a SW test harness.
