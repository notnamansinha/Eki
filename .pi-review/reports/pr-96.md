## Verdict
REQUEST CHANGES — the bounded-buffer and speed-rejection work is solid and verified, but removing the unconditional passenger fallback makes `targetStop` null-able at a non-null-asserted call site that dereferences it unguarded, a new crash path in the tracking view.

## Summary
PR #96 removes the fabricated "Tracking Area/LIVE" passenger destination fallback, consolidates the driver map's fallback center onto `DEFAULT_CENTER`, cleans up corrupted comments in `config/maps.ts`, replaces heap-allocated `String` URL/auth/payload buffers in the ESP32 firmware with bounded `char` buffers, and rejects GNSS speeds outside 0–200 km/h instead of clamping them. The hardware changes are correct and fail-closed (verified against ArduinoJson 7.4.3 source and the backend's `telemetryPayload.ts` validation contract), the comment cleanup is behavior-neutral, and the updated `securityConfig.test.ts` matches the new firmware text. The one substantive regression risk is frontend: `targetStop` can now be `null` while the tracking map still renders it through a `!` assertion, which can crash the view for routes lacking geometry. Quality is generally high; tests cover the new policy function but not the integration or the frontend change.

## Findings
- [MAJOR] `frontend/src/app/passenger/page.tsx:152-164, 298` — `targetStop` is now null-able but still passed as `targetStop={targetStop!}` into `PassengerTrackingMap` whenever `visibleView === "tracking"` (page line 296-298), which is satisfied whenever `currentView === "tracking"` and a live bus exists on the route or a ride just ended (line 174). `PassengerMap` dereferences it unconditionally: `mapCenter = { lat: targetStop.lat, lng: targetStop.lng }` (`PassengerMap.tsx:469`), `targetStop.id` (lines 554, 635), `getDistanceMeters(passengerLocation, targetStop)` (line 224) → render-time `TypeError`, and there is no `error.tsx`/error boundary under `frontend/src/app`. In the base, the fallback object was unconditional, so this was unreachable; now any tracked route with empty `stops` **and** empty `waypoints` (legacy/corrupt route docs — precisely the data class this PR series targets) crashes the view. Suggested fix: gate the map layer on the same `activeRoute && targetStop` condition already used at line 384, or make `targetStop` optional in `PassengerMap` with a placeholder render (the `!props.route` pattern already exists there).
- [MINOR] `hardware/src/main.cpp:895-898` — `if (!speedIsPlausible(rawSpeed)) return fix;` rejects the *entire* fix (position, heading, motion) even though only the speed field is bad. `evaluateTelemetry()` then treats it as fix loss: logs "[GPS] Trustworthy fix lost." and publishes one stale-position `uncertain` fix (speed 0) via `lossMessageQueued`. A transient speed glitch (multipath spike) will therefore toggle the passenger-side "GPS signal lost" banner and red `uncertain` bus marker while the position was actually fine. Rejection of the glitch is achieved as intended; consider rejecting only the speed sample (keep the fix valid with last-known/0 speed) or skipping the fix-lost messaging for speed-only rejection.
- [MINOR] `hardware/src/main.cpp:716-719, 848-852` — the guards `payloadLength >= sizeof(payload)` are correct *only* under ArduinoJson 7.4.3 semantics, which were verified from the library source: `StaticStringWriter` stores actual bytes and returns 0 when full, `TextFormatter` wraps it in `CountingDecorator` (count = actual stored bytes), and `serialize.hpp` appends the null only when `n < size` — so a full buffer (return == size) is the exact truncation signal and null-termination is guaranteed for every accepted payload. If ArduinoJson is ever bumped to a major version with "would-be length" return semantics, the guard silently stops firing. A one-line comment documenting the dependency (or switching to `measureJson()` + `size` check) would harden this. Also note the boundary shift: base allowed `payload.length() == 512/1024`, head refuses `>= sizeof` (irrelevant at real payload sizes ~130 B).
- [NIT] `hardware/src/main.cpp:61` — `authorizationHeader[DEVICE_SECRET_MAX_LENGTH + 8]` has exactly zero slack (7-char prefix + 128 max + null = 136). Safe because `deviceSecretIsValid` caps at 128 at provisioning, NVS records are validated with `boundedCStringLength`, and `initializeRequestStrings()` halts boot on any overrun (lines 333-361, 1149-1152); the endpoint buffers have 8 bytes of slack (416 vs. worst-case 410). No change needed, but the exact-fit deserves a comment.
- [NIT] `backend/src/securityConfig.test.ts:271-274` — the updated contract is purely textual: it would pass even if the buffer were sized wrong (`char authorizationHeader[4]` still contains `"char authorizationHeader["`). Consider asserting `"DEVICE_SECRET_MAX_LENGTH + 8"` and `"ENDPOINT_MAX_LENGTH"` to lock the sizing contract against future refactors.
- [NIT] `frontend/src/components/maps/DriverMap.tsx:162` — consolidation onto `DEFAULT_CENTER` shifts the no-GPS/no-stops driver map center ~0.5 km (old inline `{23.03, 72.55}` → `{23.0347, 72.5483}`). Intended and harmless, but it is a visible behavior delta in the driver UI worth a changelog mention.

## Test assessment
- `hardware/test/test_telemetry_policy/test_main.cpp:26-31` — the new `test_implausible_speed_is_rejected_instead_of_clamped` covers the inclusive bounds (0.0, 200.0 pass; -0.1, 200.1 fail) and NaN. Missing: ±infinity (`INFINITY`, `-INFINITY` — the `isfinite` branch), and there is no integration coverage for the behavior change that matters: `currentFix()` returning an invalid fix on bad speed, the `evaluateTelemetry()` fix-lost side effect, and the fact that `motionTracker` is not updated by a rejected speed. The buffer/truncation logic (initializeRequestStrings, serializeJson guards) has no automated coverage — only the claimed `platformio test` build pass.
- `backend/src/securityConfig.test.ts` — updated assertions verified character-for-character against the head `main.cpp` (`"char authorizationHeader["`, `'"Device %s"'`, absence of the old String expression, `http.addHeader("Authorization", authorizationHeader)` still present). It is a text contract, so it cannot catch semantic regressions (see NIT above).
- Frontend — **no tests touch** `passenger/page.tsx`, `DriverMap.tsx`, or `config/maps.ts`; the fallback removal and `DEFAULT_CENTER` consolidation are untested, and TypeScript's `!` hides the null path from the compiler. The claimed 75 vitest tests cover unrelated libs.

## Security assessment
The firmware change is fail-closed and verifiably safe: heap-allocated endpoint/auth/payload `String`s are replaced with static bounded buffers; `snprintf` with `%.*s` precision plus destination-size checks cannot overflow; truncation is detected via the exact `>= sizeof` condition (correct for ArduinoJson 7.4.3's actual-bytes semantics, null-termination guaranteed for accepted payloads); oversized request config halts boot rather than publishing malformed requests; credentials/device IDs are never logged. Speed validation now matches the backend contract exactly (`telemetryPayload.ts:49`: finite, 0–200 inclusive), so malformed samples are rejected at the source instead of being clamped into the accepted range. TLS/CA/auth flow is unchanged, and the repo-wide security contract test was updated to match. No new secrets, no weakened authorization, no new attack surface.

## Residual risks
- A live bus on a geometry-less route (empty `stops` + `waypoints`) now crashes the passenger tracking view with no error boundary — the primary post-merge watch item; a single bad route doc in Firestore is enough to trigger it.
- Speed glitches will flip fleet `motionState` to `uncertain` and may trip downstream "signal lost"/alerting logic that keys off the hardware `uncertain` state.
- The truncation guards depend on ArduinoJson 7.4.3's return semantics; a future major bump silently changes their meaning.
- Several open PRs touch `hardware/src/main.cpp`; merge conflicts around the refactored `publishFix`/`publishRemoteDiagnostic`/`setup()` regions are likely and must be re-verified against the v7.4.3 semantics.
- CI results (platformio native/esp32dev, vitest, backend suite) are self-reported in the PR body and were not re-run here per the read-only constraint; the security contract test now reads the working-tree `main.cpp`, so it will only validate whatever is checked out at CI time.
