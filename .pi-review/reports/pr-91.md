## Verdict
APPROVE — the change correctly fixes the root cause (cached role no longer unlocks a workspace), every code path is fail-closed, and all four protected layouts route through the shared RoleGuard; only non-blocking UX/robustness gaps remain.

## Summary
PR #91 makes cached roles display hints only: `useAuth` now keeps `loading` true while claims/Firestore verification is pending and sets `role: null` plus a `roleError` on any failure, instead of restoring `cachedRole || "passenger"` (the fail-open). RoleGuard renders a retryable "Access could not be verified" screen whenever `roleError` is set, and the old behavior of authorizing on the localStorage cache alone (including the cached-role + `permission-denied` case that silently granted admin) is gone. All protected routes (`/admin`, `/driver`, `/passenger`, `/feedback`) are wrapped by the single shared guard, and no page-level bypass remains. The change is minimal, consistent with repo patterns, and type-safe; the main gaps are a missing verification timeout (infinite spinner when offline), a dead-end error screen without sign-out, and zero test coverage for the security-critical logic.

## Findings
- [MINOR] frontend/src/hooks/useAuth.ts:77-91 — No timeout on pending verification → potential infinite spinner. The 8s `authTimeout` is cleared as soon as `onAuthStateChanged` fires, so once a cached session is restored (`setUser` with `role: null`, `loading` stays true) there is nothing bounding `getIdTokenResult()`/`getDoc()`. For an offline PWA restart, Firestore `getDoc` can pend indefinitely and the user never reaches the error screen (base behavior restored cached access instantly, so this is a regression for cached-role users — though it is the intended fail-closed tradeoff). Suggest racing verification against a bounded timer that transitions to `roleError`.
- [MINOR] frontend/src/components/shared/RoleGuard.tsx:87-107 — Error screen is a dead-end. It offers only "Try again" (`window.location.reload()`); there is no Sign out or Return Home. With persistently failing verification, the user is trapped in a reload loop: app/page.tsx:24-26 auto-redirects any signed-in, non-loading user to `/${user.role || "passenger"}`, so navigating to `/` bounces back into the error screen. Suggest adding sign-out and return-home actions.
- [MINOR] No tests added for a security-critical change. None of the 10 existing test files (frontend/src: collectionCache, rtdbResumeState, lib/*) touch `useAuth` or `RoleGuard`. The core property — role stays null until claims/Firestore verification succeeds, and `roleError` on failure — is untested, so a future refactor could silently reintroduce fail-open.
- [NIT] frontend/src/hooks/useAuth.ts:197 — The message "We could not verify your access. Check your connection and try again." is shown for *every* failure, including `permission-denied` (a server-side denial where reload won't help). Consider branching the message on error code.
- [NIT] frontend/src/hooks/useAuth.ts:208 — `logout()` sets `user: null` but never clears `roleError`. Harmless today (RoleGuard checks `!user` before `roleError`, and the next sign-in clears it at line 74), but it is a latent stale-state leak; clearing it in `logout()` would be tidier.

## Test assessment
No tests were added or updated. The logic is testable: `RoleGuard` can be tested directly by providing a mocked `AuthContext` value, and the `role: null`-until-verified / `roleError`-on-failure decision inside `useAuthState` could be extracted into a pure function and unit-tested without Firebase mocks (mocking `onAuthStateChanged`, `getIdTokenResult`, and `getDoc` otherwise requires substantial harness work — likely why the repo has no hook tests today). Missing cases: (1) cached role + claims success → role from claims; (2) cached role + claims/Firestore failure → `role: null` + `roleError` (the exact #32 scenario, including `permission-denied` with a cached admin role); (3) `loading` stays true during cached restore; (4) RoleGuard renders the error screen and withholds `children` when `roleError` is set; (5) stale-callback/generation race does not clobber state; (6) `role: null` (no error) never renders protected children.

## Security assessment
Fail-closed holds on every traced path: initial load (spinner), auth-init failure and 8s timeout (sign-in screen), signed-out (sign-in screen), cached-role restore (spinner until verification), claims success (authorized via server-issued token claims), Firestore fallback success, and every failure path (`role: null` + error screen). No path grants access from localStorage alone, and the generation guard prevents stale callbacks from mutating state. The backend independently enforces authorization from verified, revocation-aware ID tokens (`backend/src/middleware/requireAdmin.ts` checks `decoded.admin`; `requireAuth.ts` + Firestore rules gate the rest), so the client guard is defense-in-depth rather than the security boundary. Remaining exposure is inherent JWT design: a role revoked server-side stays in the local ID token claims until refresh (≤ ~1h), during which the client still shows access — server-side revocation checks cover this. No secrets, new inputs, or buffer concerns.

## Questions for author
- Was the offline/PWA scenario considered? Cached-role users can no longer enter the app offline, and there is no timeout that moves a hung verification into the error state — is an explicit verification timeout planned?
- Should the "Access could not be verified" screen include Sign out / Return Home so users with persistent failures aren't trapped in a reload loop (the home page redirects signed-in users to `/passenger`)?
- Are tests planned for this fail-closed behavior (at minimum a RoleGuard render test with mocked context)?
- Is the unconditional `roleError` message for `permission-denied` intended, or should the message distinguish "server denied access" from "network problem"?

## Residual risks
- Offline cached-role users can hang on the "Signing you in…" spinner indefinitely (no verification timeout).
- Persistently failing verification traps the user in a reload loop with no sign-out path from the error screen.
- No automated tests guard the fail-closed invariant; future refactors could regress it silently.
- Up to ~1h token-claims staleness window still authorizes revoked roles client-side (server enforcement is unaffected).
- Home-page auto-redirect (`app/page.tsx`) now sends unverifiable users to `/passenger`'s error screen rather than the landing page — cosmetic but worth watching.
