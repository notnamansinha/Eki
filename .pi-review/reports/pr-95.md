## Verdict
REQUEST CHANGES — the gate works end-to-end, but the preflight validates only `sdkconfig.defaults` while the compile-time gate backstops only 4 of the 9 required protections, leaving a fail-open path for the other 5 if the effective per-env config drifts.

## Summary
The PR hardens the fleet build in three layers: a PlatformIO pre-script (`verify_secure_fleet.py`) that fails the `esp32dev-secure` build unless 9 security options are present in `sdkconfig.defaults`, rejects any `include/secrets.h` (exact name plus credential-definition regex scan), and requires NVS persistence markers in `recovery_portal.cpp`; a compile-time `#error` gate in `main.cpp` for Secure Boot V2, flash encryption, release mode, and NVS encryption; and it retains the pre-existing runtime eFuse halt (unchanged in this diff) which runs before any NVS/config read or networking. The wiring is correct (env-scoped `extra_scripts`, `raise` aborts the build, CI builds the signed fleet env with an ephemeral key), the docs edits are accurate, and the regex re-run against the actual repo confirms no false positives in legitimate code — the only match is the stale gitignored `secrets.h` template sitting in the working tree. The main gap: the preflight reads only the defaults file, not the generated per-env `sdkconfig.esp32dev-secure`, and only 4 of the 9 options have a compile-time backstop, so five protections (`CONFIG_SECURE_BOOT`, `CONFIG_SECURE_BOOT_BUILD_SIGNED_BINARIES`, `CONFIG_SECURE_DISABLE_ROM_DL_MODE`, `CONFIG_NVS_SEC_KEY_PROTECT_USING_FLASH_ENC`, `CONFIG_ESP32_REV_MIN_3`) can be silently weakened by a stale or tampered local generated config.

## Findings
- [MAJOR] hardware/scripts/verify_secure_fleet.py:8 — Preflight validates only `sdkconfig.defaults`, not the effective per-env generated config (`sdkconfig.esp32dev-secure`, which is gitignored at hardware/.gitignore:15 and reused across builds). ESP-IDF preserves existing `sdkconfig` values over `sdkconfig.defaults` on merge, so a stale/tampered generated config disables an option while the preflight still passes. The compile-time gate (hardware/src/main.cpp:32-46, PR version) backstops only 4 of the 9 options (SB V2, flash enc, release mode, NVS enc); `CONFIG_SECURE_BOOT`, `CONFIG_SECURE_BOOT_BUILD_SIGNED_BINARIES`, `CONFIG_SECURE_DISABLE_ROM_DL_MODE`, `CONFIG_NVS_SEC_KEY_PROTECT_USING_FLASH_ENC`, and `CONFIG_ESP32_REV_MIN_3` have no effective-config check. Suggested fix: extend the `#error` gate to all nine options and/or have the preflight also parse the generated per-env `sdkconfig` file.
- [MINOR] hardware/scripts/verify_secure_fleet.py:57 — The NVS persistence check is a string-presence heuristic, not a behavioral check: it requires the exact literal `preferences.putBytes(CONFIG_KEY, &candidate_, sizeof(candidate_))`. Any innocuous refactor (e.g., dropping `&` via pointer decay) fails the build (false positive, fail-closed but brittle), while the markers appearing anywhere in the file (even in dead code) passes without proving the provisioning path persists to NVS. Suggested fix: scope the check to the provisioning function or keep as-is but document the brittleness.
- [MINOR] hardware/scripts/verify_secure_fleet.py:29-38 — `secrets.h` rejection is exact-case, exact-name, single-path (`include/secrets.h`). On case-sensitive filesystems (CI: ubuntu), a `Secrets.h`/`secret.h` or a copy under `lib/` bypasses the explicit check; the regex scan catches `#define`/`-D`/`CONFIG_` definitions only for the five name patterns (e.g., `#define MQTT_PASSWD` or constexpr-based secrets would slip through). No such files exist today, so this is defense-depth only.
- [NIT] hardware/include/secrets.h (untracked, gitignored template present on disk) — A stale legacy template (contains `#define WIFI_SSID`, `DEVICE_SECRET`) currently sits in the working tree; any local `platformio run -e esp32dev-secure` will now fail the preflight until it is deleted. This is the intended mechanism working (verified: it is the only file matching the credential regexes), but the READMEs could tell developers to remove any legacy `secrets.h`.
- [NIT] hardware/src/main.cpp:1052-1056 — The retained runtime halt loop (`while (true) delay(1000);`) has no `esp_task_wdt_reset()`; if the Task WDT is armed the device will watchdog-reset in a loop rather than halt quietly. Still fail-closed (device never reaches config/networking), and pre-existing — not introduced by this PR.
- [NIT] hardware/scripts/verify_secure_fleet.py:22-27 — Non-compliance surfaces as a raw `RuntimeError` traceback. Fail-closed and correct (PlatformIO aborts with non-zero exit), but a one-line message with `sys.exit`/clean error text would be more operator-friendly.

Verified-good (no action): preflight is env-scoped to `[env:esp32dev-secure]` only (platformio.ini:29, PR version), so dev/native builds are unaffected; `pre:` + `raise` correctly fails the build; working dir via `env.subst("$PROJECT_DIR")` is absolute; all 9 required lines are present in `sdkconfig.defaults` (lines 13-25); the compile gate sits after includes that pull in `sdkconfig.h` (`Arduino.h`, `esp_attr.h`); the runtime gate (main.cpp:1044-1056) runs before `recoveryAccess.loadOrCreate()` (~1058) and `deviceConfiguration.load()` (1062), and before WiFi/publisher-task startup; `EKI_FLEET_BUILD=0` dev env is untouched; CI (`.github/workflows/ci.yml:56-59`) exercises the positive path with an ephemeral 3072-bit key; both README edits and their `../operations/HARDWARE_SECURITY_PROVISIONING.md` link are accurate.

## Test assessment
No tests were added or modified by this PR. CI covers only the positive path: `platformio run --project-dir hardware -e esp32dev-secure` (ci.yml:59) exercises the preflight, the compile-time gate, and real Secure Boot V2 signing; the native suite (`platformio test -e native`) is untouched and none of the existing tests reference `EKI_FLEET_BUILD`, secure boot, flash encryption, or the preflight. Missing coverage, all failure paths:
- Preflight negative cases: a missing/renamed required option fails; an option set to `=n` fails; `include/secrets.h` present fails; a renamed credential file (e.g., `Secrets.h` with `#define WIFI_SSID`) fails; NVS markers absent fails; all-clear passes.
- Compile-time negative case: build `esp32dev-secure` with one required option disabled in the effective config and assert the `#error` fires.
- The regex suite has no unit tests (patterns could be extracted and tested against fixtures to lock in no-false-positive/no-false-negative behavior).
Suggest a small pytest that runs the script's logic against a temp project, since the script is plain Python and cheaply testable.

## Security assessment
The design is fail-closed in the right places: pre-build (preflight), compile time (`#error`), and runtime (eFuse halt before NVS config read or networking), with no plaintext secrets remaining in tracked source (verified: `secrets.h` is untracked/gitignored and nothing includes it). The main security weakness is the effective-config drift gap for five protections (MAJOR above): a local generated `sdkconfig.esp32dev-secure` with those options disabled would produce a fleet image the preflight cannot see and the compiler does not check. The secrets.h rejection is robust for the exact known vector and adequately covers renamed variants via the regex scan for the common naming patterns. Runtime failure mode is safe (infinite halt/reboot-loop, no network or config access).

## Residual risks
- Effective-config drift can silently disable 5 of the 9 protections for local fleet builds until the compile gate is extended or the preflight also scans the generated per-env sdkconfig.
- Local machines with the leftover gitignored `secrets.h` template will see fleet builds fail until the file is deleted — safe direction, but may read as a false failure.
- The preflight makes `esp32dev-secure` builds dependent on `scripts/verify_secure_fleet.py` and `sdkconfig.defaults` existing; any packaging/CI step that omits them fails closed (acceptable, worth knowing).
- The compile gate depends on `sdkconfig.h` macros being defined by the framework headers; symbol names are pinned by `espressif32@7.0.1`, so an IDF/platform bump that renames Kconfig symbols will trip the gate (fail-closed) until updated.
- PR body claims (22 native tests passed, `esp32dev` build passed) were not independently verified due to the read-only/no-build constraint; CI is the verifier.
- Watch in CI: the firmware job now fails if the preflight or `#error` trips — any future `sdkconfig.defaults` edit must keep all nine lines, or the fleet build breaks loudly (which is the point).
